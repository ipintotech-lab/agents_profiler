What this tab does, and what to expect

Upload traces your own agent produced and the app looks for work it repeats: the same call with the same input, the same chain of steps, LLM calls that only pick the next step. Each one is a place to save tokens.

  1. Choose one or more files — JSON or JSON Lines: agent trace events, Claude Code session files (~/.claude/projects/…/*.jsonl), or common trace exports. The format is detected for you.
  2. Pick a workflow — the report covers one at a time; by default the one with the most events.
  3. Click "Run pipeline" at the bottom.

What to expect: findings need repeats, so a few runs usually show little. A trace missing tokens, cost or timing still works, and a note at the top of the report says what's missing and what that changes.

What the report shows (after "Run pipeline"):

  • 01 Summary — where the money goes and what to change: each repeat worth fixing, the evidence, the observed saving and the fix (cache it, use a rule, script the steps).
  • 02 Repetition — the same steps in the same order across runs, the same call with the same input, and compiled workflows: one step order per task, checked on held-out runs. Set "Step order" to the ASP solver to compare its order with the simple one.
  • 03 Nodes — every distinct operation, costliest first, and whether the same input ever gave a different result.
  • 04 Behavior — per action: cost (typical and worst 5%), consistency, models and versions, which input field decides the answer, and regions: input values where a simple rule gives the answer while the rest needs the LLM. Tick "Keep these events in history" to add uploads up over time.
  • 05 Upload contents — what was read: events, runs, workflows.
New here? How to read a Hugging Face dataset
  1. Paste a dataset link — the dataset page's address, or a link to one file (…/blob/main/swebench.jsonl). Try one:
  2. Click "List files" and pick one — only JSON / JSON Lines files are listed (.zst / .gz included; Parquet isn't supported). Pick a data file such as swebench.jsonl or release/<week>/traces/<day>.jsonl.zst, not a manifest or report.
  3. Set "Records" — how many sessions to read from the start of the file. Start with 10 (max 500).
  4. Gated dataset? Add a token — if the dataset page shows an access form:
    1. sign in at huggingface.co and submit the form on the dataset page (some datasets approve by hand, so it can show "pending");
    2. create a token at huggingface.co/settings/tokens — type Read, or fine-grained with "Read access to contents of all public gated repos you can access" ticked;
    3. paste it in the Token field below. It's sent only to this server, for this request.
  5. Click "Run pipeline" at the bottom.
HTTP 401 — no token given (step 4). HTTP 403 — the token has no access yet: the request is pending, was made from another account, or a fine-grained token lacks the gated-repos permission.

What this tab does, and what to expect

A health check of the app itself, not of your data. It generates fresh sample data for 24 settings, one change at a time from a fixed baseline, and runs each through the whole pipeline:

  • number of agents (1 to 6) and how much answers vary (low / mid / high);
  • trace size (1,000 to 10,000 lines);
  • capacity settings (how peak demand is measured, headroom, cost and value overrides).

What to expect: all 24 pass in under a minute. Each row shows whether the run finished, how long it took, how many planted findings were found, the regions the behavior analysis found (and whether the planted one was among them; it shows up only in the larger traces), and how many "same answer every time" calls matched the known answer. A FAIL means the pipeline crashed on that setting; the error is in the row.

What this POC does, and what it should find

On real agent traces nobody knows the right answers, so there is nothing to grade the app against. This POC builds six mock agents where we do know: each was written on purpose to contain specific things worth fixing (a lookup to cache, an LLM choice a simple rule could make, a fixed chain of steps, an LLM step that gives different answers to the same input) and a few traps the app should leave alone. It then runs the app on their traces and checks what it finds.

  1. Generate traces from the six agents: security (CVE), support, release, code review, data pipeline and sales.
  2. Pick the cut-offs the app uses to decide "this step always gives the same answer" (the calibration datasets below).
  3. Test those cut-offs on new datasets at growing sizes, from 100 to 10,000 trace lines, to find the point where more data stops changing the answers.
  4. Check that the app's #1 "fix this first" pick is the same across datasets.
  5. Estimate the money saved by caching (modeled, not measured).
  6. Compare what each agent was built to contain with what the app actually found (Phase 6), including the behavior analysis's regions: an action that is rule-like only for some inputs.

What to expect when you run it (default settings, about 15 seconds; measured on this version):

  • About 15 of 18 built-in findings found at 2,000 lines, 17 at 5,000 or more. Usually missed: analyze_remediation and diagnose_failure, which give a different answer only 20% of the time. That is subtle and needs more data to see.
  • The region in analyze_remediation (rule-like only for high/critical CVEs) shows up from 5,000 lines: it needs about 15 calls per severity before it beats chance.
  • No traps flagged from 2,000 lines on. With fewer lines an occasional false alarm can show up: a few repeats aren't enough to tell luck from a pattern.
  • Around 15 "found, not planted". Mostly LLM steps that happened to give the same answer to the same input in this data, e.g. "cache classify_severity". They are real in the data, just not built in on purpose.
  • Almost nothing below 500 lines: every finding needs the same input to show up more than once.
  • The verdict depends on how many datasets you use. With 5 + 5 it usually says SUPPORTED (settles at 2,000 lines). With 30 + 30 it says NOT YET SUPPORTED: more datasets expose one wrong call at the default cut-offs, so a stricter cut-off is picked, and then the app can judge only about a third of the steps, below the bar for "settled". That is an honest result, not a bug.

The mock agents are simpler than real ones, so matching them doesn't prove the app is right on real traces. Each miss or false alarm is a concrete case to look at.

What this tab does, and what to expect

A FinOps view of agent spend: across every agent in the data, how much went to LLM and tool calls, how much of it these traces show was avoidable, and which savings have the lowest observational risk. It uses the same evidence as the other tabs (repeated calls, repeated step chains, LLM choices a rule could make, regions), across all agents at once.

  1. Pick the data: click Load demo data (six mock agents, 5,000 trace lines), or choose JSON / JSON Lines files, or paste a Hugging Face dataset link. Aggregate usage exports (token counters per workload, or agent/trigger activations; JSON, JSON Lines or CSV) get a usage report instead: concentration, cache-read share and outliers, with no $ figures.
  2. Optional: runs per month. Traces carry no dates, so there is no "this month". Give your monthly run volume and every $ figure is also shown as a monthly projection (observed cost per run × runs).
  3. Click Analyze spend.

How to read the numbers: avoidable is the cost of observed calls a change would have removed, each action counted once, so it is a minimum, not a forecast. Risk is a rule of thumb from how much evidence there is and what kind of change it is; nothing has been replayed against past calls yet. Real traces without recorded cost show $0: the coverage card says so.

Tell us about the agent (optional)

Traces show what happened; they don't say what a mistake costs or what you'd let us change. Your answers can only make the findings stricter or fill in what the traces leave out, and the report marks every conclusion that rests on them. Nothing here is verified. Leave it all blank to analyze the traces alone.

What the terms mean
node
One kind of operation, e.g. Bash: git push or Read: .py.
llm_call ← Bash
The LLM call made right after a Bash result: the model reading it and deciding what to do next.
starting point (trigger)
What an action reacted to: the user's prompt, or the result of the previous step.
LLM calls between steps
Calls whose only job was to choose the next step. A script that runs the steps in order doesn't need them.
deterministic
The same input always gave the same result, seen often enough to trust it.
non-deterministic
The same input gave different results at least once.
insufficient evidence
The same input wasn't repeated enough times to judge.
business fingerprint
"Same request": the same node, starting point and input.
context fingerprint
Same request and the same result from the step that triggered it.
execution fingerprint
Same request, same triggering result, same model and agent version.
agreement
Across requests seen more than once, how often they got their most common answer. 100% means repeats always matched.
dominant output · dominant rate
The most common answer for a request, and how often it came back ("same answer 9 of 10 times" = 90%).
result A, B, …
Tool outputs are stored as hashes, so different outputs are lettered within each row instead. Same letter = identical output.
redundant
Repeats after the first that returned exactly the same output.
saving
The observed cost of the calls that wouldn't have run. Measured from these traces, not forecast.

      01Summary — how much data the profiler needs before its answers stop changing
      
    
      This answers one question: how much synthetic trace data does the profiler actually need before its determinism calls stop changing? It is not looking for the sample size with the highest accuracy — it is looking for the smallest sample size beyond which feeding it more data stops meaningfully improving the result. Below that point, trust the numbers less; above it, more data is just cost with no added benefit.
      
    
      How it gets there, phase by phase: (1) pick the best determinism thresholds by voting across several independent "calibration" datasets; (2) freeze those thresholds and re-run the profiler at increasing sample sizes on a completely separate set of "validation" datasets, watching where accuracy/recall/coverage level off; (3) check that the profiler's worst-offender recommendation is stable at that sample size, not a coin flip between seeds; (4) sanity-check the resulting B-POP capacity recommendation against the same workload; (5) model what the measured determinism rate would be worth in avoided LLM calls; (6) compare what each of the six mock agents was built to contain with what the report actually found. Every phase grades all six agents' workflows. Calibration and validation always use non-overlapping seeds, so the thresholds are never graded on the same data they were chosen from.
